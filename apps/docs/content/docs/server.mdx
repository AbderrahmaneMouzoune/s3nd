The use case s3nd is built for has three parts: an app whose data lives in IndexedDB, a bucket
you control, and a server between them. This page is the middle one — what to deploy, what to
configure on it, and how to know it works.

You need it as soon as a **browser** takes part in a transfer. A browser cannot hold S3
credentials, and a bucket opened to the web is a bucket anyone can read. The server holds the keys
and answers [four routes](/docs/protocol) instead.

If every participant is a machine you control — your laptop, a CI runner, a backup box — you can
skip it entirely and point the CLI at the bucket. That is [the next page](/docs/no-server).

## The route

The handler takes a `Request` and returns a `Response`, so it mounts anywhere. In a Next.js app,
one file is the whole server:

```ts title="app/api/transfers/[[...route]]/route.ts"
import { createBucket, createTransferHandler } from '@s3nd/core'

const bucket = createBucket({
  bucket: process.env.S3ND_BUCKET!,
  prefix: 'transfers',
  maxSize: 4 * 1024 * 1024,
})

export const { GET, POST, DELETE } = createTransferHandler({
  bucket,
  app: 'notes',
  maxVersion: 3,
  expiresIn: 3600,
  authorize: async (request) => request.headers.get('authorization') === `Bearer ${process.env.S3ND_TOKEN}`,
})
```

The route runs on the Node runtime, Bun or Deno. On Next.js that is the default; do not opt the
route into `export const runtime = 'edge'`, which is not supported. See
[runtimes](/docs/installation#runtimes) for the full list, and for Cloudflare Workers.

<Callout>
  `basePath` defaults to `/api/transfers`. Mount the routes anywhere else and pass the same path, or `GET /:code` reads
  a code off the wrong segment.
</Callout>

The catch-all segment matters: the handler serves `/`, `/:code` and `/:code/raw`, so the route file
has to receive all three.

| Option           | What to set it to                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------- |
| `bucket`         | A `Bucket`. Give it a `prefix` — transfers should not share a namespace with anything else. |
| `app`            | Your app's name. It is recorded in every snapshot, so a bucket says what wrote it.          |
| `maxVersion`     | The newest schema this deployment understands. Older builds then refuse newer snapshots.    |
| `expiresIn`      | Seconds. An hour is right for a device handover; `null` never expires.                      |
| `authorize`      | See below. Without it every route is public.                                                |
| `raw`            | `'stream'` pipes bytes through your server; `'redirect'` answers 302 with a presigned URL.  |
| `onError`        | A logger for the failures that answer `INTERNAL`. See below.                                |
| `maxRequestSize` | Bytes of request body accepted. Set it on a self-hosted server. See below.                  |

## When something breaks

Every failure answers JSON, `{ error: { code, message } }`, including the ones nobody planned
for: an `authorize` that throws, an S3 call that fails, a network error. Those answer `INTERNAL`
(500) with the message `Internal error.` and nothing more, because the raw message can name your
bucket or carry SDK internals. A path that is not validly percent-encoded, `/api/transfers/%E0`,
answers `INVALID_SYNC_CODE` (400) like any other code that cannot exist.

`onError` is where the real error goes, with the request that caused it:

```ts
createTransferHandler({
  bucket,
  onError: (error, request) => console.error(`s3nd: ${request.method} ${request.url}`, error),
})
```

It is only called for the failures that answer `INTERNAL`, not for an unknown code or a refused
request, and an error thrown inside it is ignored: logging cannot cost the client its answer.

## Credentials

Nothing in the browser ever sees them. On a managed runtime, prefer the role over a key pair —
nothing to rotate, nothing to leak:

```ts
// Lambda, ECS, Fly, a VM with an instance role: the SDK finds them.
const bucket = createBucket({ bucket: process.env.S3ND_BUCKET! })
```

Where there is no role — Vercel, most container hosts — set the variables and let the default chain
read them:

```sh
S3ND_BUCKET=notes-transfers
S3ND_REGION=eu-west-3
AWS_ACCESS_KEY_ID=…
AWS_SECRET_ACCESS_KEY=…
```

On R2 the same server needs an endpoint instead of a region:

```ts
const bucket = createBucket({
  bucket: process.env.S3ND_BUCKET!,
  endpoint: `https://${process.env.R2_ACCOUNT_ID}.r2.cloudflarestorage.com`,
  credentials: {
    accessKeyId: process.env.R2_ACCESS_KEY_ID!,
    secretAccessKey: process.env.R2_SECRET_ACCESS_KEY!,
  },
  prefix: 'transfers',
})
```

Whatever it runs on, the token wants exactly three verbs on one bucket — `s3:PutObject`,
`s3:GetObject`, `s3:DeleteObject` — and nothing else. A transfer server that can list a bucket is a
transfer server that can enumerate everyone's codes.

## Authorization

`authorize` runs before anything else. Return `false` for a plain 401, or a `Response` to answer
with your own.

**A personal drop box behind a proxy.** Nothing to do: leave `authorize` off and let the proxy in
front decide who reaches the route.

**A shared token**, for a CLI and for CI:

```ts
authorize: (request) => request.headers.get('authorization') === `Bearer ${process.env.S3ND_TOKEN}`
```

**A signed-in user**, which is what an app with accounts wants:

```ts
authorize: async (request) => {
  const session = await auth(request)
  if (!session) return Response.json({ error: { code: 'UNAUTHORIZED', message: 'Sign in first.' } }, { status: 401 })

  return true
}
```

Two things the check does not do, and should:

- **It does not scope a code to a user.** Anyone signed in who guesses a code reads what it holds.
  At 40 bits and an hour of life, guessing is not the attack to worry about — but do rate-limit
  `GET /:code` at the edge, because a code is the only secret protecting a snapshot.
- **It does not limit how much one account stores.** `maxSize` caps a single transfer, not the
  number of them. Count them per user if the route is public to your users.

## One prefix per purpose

The `prefix` is the seam that lets each kind of object have its own lifetime:

```ts
createBucket({ bucket: 'notes-data', prefix: 'transfers' }) // codes, expire in a day
createBucket({ bucket: 'notes-data', prefix: 'backups' }) // per-account, never expire
```

`expiresIn` stops a transfer being handed over; it does not delete the object. That is an S3
lifecycle rule's job, per prefix — a day or two for `transfers/`, nothing at all for `backups/`.
Forget it and the bucket fills up silently, which is the single most common way a s3nd
deployment goes wrong. [`s3nd doctor`](/docs/cli) checks for it.

## Request limits

The payload goes through your runtime, so its request limit is your transfer limit: 4.5 MB on
Vercel serverless functions, 6 MB on synchronous Lambda. A snapshot travels as plain JSON and is
only gzipped on its way to S3, so that limit applies to the uncompressed JSON.

**On a self-hosted server, set `maxRequestSize`.** Node, Bun or Deno behind your own proxy has no
platform limit in front of it, and without one a client can make the handler hold an arbitrarily
large body in memory. `maxRequestSize` bounds the incoming body, in bytes, for snapshots and files
alike:

```ts
createTransferHandler({ bucket, maxRequestSize: 10 * 1024 * 1024 })
```

A `Content-Length` above it answers `TOO_LARGE` (413) without reading anything. A body with no
`Content-Length`, or one that understates it, is read with a counter and cut off as soon as it
passes the limit. A snapshot's JSON is bounded before it is parsed.

Left unset, files default to the bucket's `maxSize` when it has one, and snapshots to no limit, so
an existing deployment behaves as before. The bucket's `maxSize` still applies on top: it measures
what is stored, after gzip for a snapshot. For downloads, `raw: 'redirect'` keeps the bytes off
your server entirely. See [limits](/docs/limits).

## Files past the request limit

With `upload: 'presign'`, a file never goes through your server. The client asks for a signed
URL, sends the bytes straight to the bucket, then asks the server to check them and make the code
live. Your runtime's request limit stops applying to files; snapshots keep going through the
route, as before.

```ts title="app/api/transfers/[[...route]]/route.ts"
export const { GET, POST, DELETE } = createTransferHandler({
  bucket,
  upload: 'both', // 'proxy' (the default), 'presign', or 'both'
  presignExpiresIn: 900, // how long the upload URL is accepted, in seconds
})
```

```ts
const transfers = createTransferClient({ baseUrl: '/api/transfers', upload: 'auto' })

await transfers.createFile({ body: file, filename: file.name, onProgress: ({ loaded, total }) => {} })
```

The signature covers the exact size and content type the client announced, so the bucket refuses
anything else, and `maxSize` is checked before a URL is signed. On completion the server checks
the stored size again. `'auto'` on the client tries a presigned upload and falls back to the route
when the server does not offer one. The flow is specified in
[`PROTOCOL.md`](https://github.com/AbderrahmaneMouzoune/s3nd/blob/main/packages/protocol/PROTOCOL.md).

Two things on the bucket make it work:

**A CORS rule**, because the browser now talks to the bucket. It needs `PUT` from your app's
origin, with the `content-type` header. [`s3nd doctor`](/docs/cli) checks for one.

```json title="Bucket CORS"
[
  {
    "AllowedOrigins": ["https://app.example.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

**A lifecycle rule on `pending/`**, inside your prefix. An upload that is never completed stays
there, never handed over, until a rule removes it. A rule on the whole prefix (`transfers/`)
already covers it.

```jsonc
{
  "Rules": [
    {
      "ID": "abort-unfinished-presigned-uploads",
      "Status": "Enabled",
      "Filter": { "Prefix": "transfers/pending/" },
      "Expiration": { "Days": 1 },
    },
  ],
}
```

A single presigned `PUT` is capped at 5 GiB by S3.

## When the app is on another origin

Same-origin — the app and the route in one Next.js deployment — needs no CORS at all, which is the
configuration to prefer. If the app is served from somewhere else (another domain, an extension, a
PWA hosted elsewhere), pass `cors`:

```ts title="app/api/transfers/[[...route]]/route.ts"
export const { GET, POST, DELETE, OPTIONS } = createTransferHandler({
  bucket,
  app: 'notes',
  cors: {
    origin: ['https://notes.example.com'], // or (origin) => boolean, or '*'
    credentials: false,
    maxAge: 600,
  },
})
```

|               |                                                                                                    |
| ------------- | -------------------------------------------------------------------------------------------------- |
| `origin`      | The page origins allowed: a list of exact origins, a predicate, or `'*'` for any                   |
| `credentials` | Lets the browser send cookies along. Cannot be combined with `'*'`: `createTransferHandler` throws |
| `maxAge`      | Seconds a browser may cache the preflight answer                                                   |

With it, the handler answers the `OPTIONS` preflight with `204`, before `authorize` runs (a
preflight carries no credentials), and allows `content-type`, `authorization`, `s3nd-protocol` and
`x-s3nd-filename`. Every other response carries the CORS headers too, errors included, so the page
can read a `401` or a `TOO_LARGE` instead of seeing an opaque network failure. `s3nd-protocol` and
`content-disposition` are exposed to the page.

An origin that is not allowed gets no CORS headers at all, and the browser withholds the response.
A predicate that throws refuses the origin. Without `cors`, nothing is added and `OPTIONS` answers
`INVALID_REQUEST`, as before.

Remember to export `OPTIONS` from the route: a Next route handler only answers the methods it
exports.

## Proving it works

The CLI speaks the same protocol, so a deployment can be checked from a terminal with no S3
credentials on it at all:

```sh
$ s3nd doctor --remote https://notes.example.com/api/transfers --token "$S3ND_TOKEN"
✓ Server: https://notes.example.com/api/transfers answered
✓ Create, read, delete: round-tripped code 8WTXQC8R
```

It creates a transfer, reads it back, deletes it, and exits non-zero if any of that fails — which
makes it a deployment smoke test:

```yaml title=".github/workflows/deploy.yml"
- run: npx @s3nd/cli doctor --remote ${{ vars.TRANSFER_URL }} --token ${{ secrets.S3ND_TOKEN }} --json
```

Keep the deployment in a [profile](/docs/cli#profiles) and the flags disappear:

```json title="s3nd.config.json"
{
  "profiles": {
    "prod": { "remote": "https://notes.example.com/api/transfers", "token": "${S3ND_TOKEN}" },
    "local": { "remote": "http://localhost:3000/api/transfers" }
  }
}
```

```sh
s3nd -p prod doctor
s3nd -p local put ./fixture.json
```

## The app side

The browser half is `@s3nd/protocol`, or [the React hooks](/docs/react) that wrap it. Neither can
reach the AWS SDK, so no amount of refactoring in the app can put a credential in a bundle:

```ts
const transfers = createTransferClient({ baseUrl: '/api/transfers' })

const { code } = await transfers.createSnapshot({ data: await dumpIndexedDb(), version: 3 })
```

---
title: 'The transfer protocol'
description: 'Four HTTP routes between a s3nd server and anything that talks to it — written down, so it is not just whatever the handler happens to do.'
---

A browser cannot hold your S3 credentials, so a transfer always has a server in the middle. The
shape of that middle is this protocol: four routes, one error format.

It is written down rather than left implicit for three reasons. A client works against any server
that answers these routes, not only against `createTransferHandler()`. A server written in Go or
Rails works with every s3nd client. And the CLI pointed at `--remote` cannot tell which of
those it is talking to — which is exactly why `s3nd put` works against your own deployment.

<Callout>
  This page is a tour. The normative text is
  [`PROTOCOL.md`](https://github.com/AbderrahmaneMouzoune/s3nd/blob/main/packages/protocol/PROTOCOL.md), shipped in
  `@s3nd/protocol`: when you implement a server or a client, follow that one. Where the two disagree, `PROTOCOL.md`
  wins.
</Callout>

## Serving it

```ts title="app/api/transfers/[[...route]]/route.ts"
import { createBucket, createTransferHandler } from '@s3nd/core'

export const { GET, POST, DELETE } = createTransferHandler({
  bucket: createBucket({ bucket: 'my-bucket' }),
  app: 'notes',
  expiresIn: 3600,
})
```

The handler takes a `Request` and returns a `Response` — nothing else. That is a Next route
handler, a Hono route, `Bun.serve`, Deno, or a worker, without an adapter for any of them.
[Setting up a server](/docs/server) configures the rest of it: credentials, authorization, expiry,
request limits and CORS.

<Callout type="warn">
  Every route is public unless you pass `authorize`. For a personal drop box behind a proxy that is what you want; for
  anything else it is not.
</Callout>

```ts
createTransferHandler({
  bucket,
  authorize: async (request) => request.headers.get('authorization') === `Bearer ${process.env.TOKEN}`,
})
```

Return `false` for a plain 401, or a `Response` to answer with your own.

## Talking to it

```ts
import { createTransferClient } from '@s3nd/protocol'

const transfers = createTransferClient({ baseUrl: 'https://drop.example.com/api/transfers' })

const { code } = await transfers.createSnapshot({ data: state, version: 3 })
const incoming = await transfers.read(typedCode) // null when unknown or expired
```

`@s3nd/protocol` is `fetch` and nothing else. It has no runtime dependencies, and no
path from it reaches the AWS SDK — so it bundles for a browser, a worker or React Native without
dragging a storage client along. That is the reason it is a separate package rather than a subpath
of `s3nd`: a subpath would have put the SDK in every front-end's `node_modules`.

It checks what comes back instead of casting it. A `2xx` that is not JSON (an SSO login page, a
`baseUrl` pointing at the wrong place) or JSON without a string `code`, a known `kind` and a
`createdAt` rejects with a `TransferError` coded `INTERNAL`, whose message names the status and the
content type received, rather than a `SyntaxError` or a code reading "undefined".

A request to a server that never answers waits forever by default. Pass `timeout`, in
milliseconds, to bound every call, reading the response included:

```ts
const transfers = createTransferClient({ baseUrl, timeout: 15_000 })
```

Past it, the call rejects with a `TransferError` coded `TIMEOUT`. That code is the client's own: no
server sends it, so it is not in the table below, and its type is `TransferClientErrorCode` rather
than `TransferErrorCode`. A `signal` you pass still works alongside the timeout, and aborting it
still rejects with the plain `AbortError`, which the React hooks treat as a silent cancel while
they show `TIMEOUT` as an error.

In React you rarely call it directly — [the hooks](/docs/react) wrap it.

## The version header

Every request a client sends carries `s3nd-protocol: 1`, and every response the handler sends
carries it back, errors included. A request announcing a newer version is refused with
`UNSUPPORTED_PROTOCOL` before anything reads its body, so a future client learns it is talking to
an older server instead of being misread. A request without the header is answered as version 1,
which is what clients from before the header speak.

```ts
import { PROTOCOL_HEADER, PROTOCOL_VERSION } from '@s3nd/protocol'
// 's3nd-protocol', 1
```

A new optional field or a new error code does not bump the version; clients ignore fields they do
not know and treat an unknown error code as `INTERNAL`.

## The routes

All of them are relative to wherever you mounted the handler, `/api/transfers` by default.

### `POST /`

Creates a transfer and returns the code. What you send decides what it holds.

The server decides what the transfer is, in this order:

1. **`X-S3nd-Filename` present**: a **file**, whatever the `Content-Type`. The body is the raw
   bytes, and the header carries the original filename, percent-encoded. A `.json` file is sent
   as `application/json` and stays a file.
2. **Otherwise, `Content-Type: application/json`**: a **snapshot**. The body is
   `{ data, version?, device? }`, structured state handed back inline on read. `device` is stored
   as sent; without it the snapshot has none, and the server does not fill it in.
3. **Otherwise**: a **file** named `file`.

`createFile()` always sends the filename and `createSnapshot()` never does, so a client built on
`@s3nd/protocol` lands on the right side without thinking about it.

```json title="201"
{ "code": "K7QP2M4X", "kind": "snapshot", "createdAt": "…", "expiresAt": "…", "size": 412 }
```

The server picks the code, never the client — it retries a fresh one on the rare collision rather
than overwriting a live transfer.

### `GET /:code`

Everything known about a transfer. For `kind: "snapshot"` the state comes back inline as `data`;
for `kind: "file"` it does not, and you fetch `/raw` instead.

```json title="200"
{
  "code": "K7QP2M4X",
  "kind": "snapshot",
  "createdAt": "…",
  "expiresAt": "…",
  "device": "Pixel 8",
  "app": "notes",
  "version": 3,
  "data": { "notes": [] }
}
```

The code is normalized before lookup, so whatever the user typed — lowercase, grouped with spaces
or dashes, `O` where they meant `0` — resolves to the same transfer. See
[sync codes](/docs/sync-codes).

### `GET /:code/raw`

The bytes of a file, with the stored `Content-Type` and a `Content-Disposition` carrying the
filename. With `raw: 'redirect'` the handler answers `302` with a presigned URL instead, so the
payload never transits your server twice.

`/raw` serves files only: on a snapshot code it answers `NOT_FOUND`. A snapshot's state comes from
`GET /:code`.

Files only. A snapshot has no raw form, so its code answers `404 NOT_FOUND` with the same body as
an unknown or expired code: `/raw` says nothing about what a code holds. A snapshot's state comes
from `GET /:code`.

### `DELETE /:code`

Burns a code, and answers `204`. Deleting one that is already gone is not an error — a client that
burns a code after a successful restore should not have to care whether it won that race.

### Presigned uploads: `POST /` with `upload: "presign"`, then `POST /:code/complete`

A server with `upload: 'presign'` or `'both'` also takes a file without its bytes. The client
posts `{ "upload": "presign", "filename", "size", "contentType" }` as JSON and gets back
`{ code, uploadUrl, method: "PUT", headers, expiresAt }`. It sends the bytes to `uploadUrl`, then
calls `POST /:code/complete`. The server checks the stored object and answers the usual `201`.
Until then the code reads as `NOT_FOUND`.

A server in `proxy` mode, the default, answers the presign request with `400 INVALID_REQUEST`, and
so does one that predates it, so a client can try and fall back. The full flow, with what each side
MUST check, is in
[`PROTOCOL.md`](https://github.com/AbderrahmaneMouzoune/s3nd/blob/main/packages/protocol/PROTOCOL.md).

## Errors

Every non-2xx answer carries the same body, unexpected failures included:

```json
{ "error": { "code": "NOT_FOUND", "message": "Unknown or expired code." } }
```

| `code`                 | HTTP  | What happened                                                        |
| ---------------------- | ----- | -------------------------------------------------------------------- |
| `INVALID_REQUEST`      | `400` | Malformed body, or a method the route does not serve                 |
| `INVALID_SYNC_CODE`    | `400` | What was typed cannot be a code in this alphabet                     |
| `UNSUPPORTED_PROTOCOL` | `400` | The request announced a newer protocol version                       |
| `UNAUTHORIZED`         | `401` | `authorize` refused                                                  |
| `NOT_FOUND`            | `404` | No such code — or it expired                                         |
| `CODE_TAKEN`           | `409` | No free code found; vanishingly unlikely at 40 bits                  |
| `SNAPSHOT_TOO_NEW`     | `409` | Written by a newer schema than this deployment reads                 |
| `TOO_LARGE`            | `413` | Over the configured `maxSize`, refused before the whole body is read |
| `INTERNAL`             | `500` | Anything else                                                        |

`NOT_FOUND` deliberately covers expiry as well as absence. Distinguishing them would let someone
probe which codes have been used.

Clients throw `TransferError`, which carries that `code` — branch on it rather than on status codes
or message text:

```ts
import { isTransferError } from '@s3nd/protocol'

try {
  await transfers.createSnapshot({ data: state })
} catch (error) {
  if (isTransferError(error) && error.code === 'TOO_LARGE') {
    // ask the user to trim their database
  }
}
```

## Expiry is enforced on read, not by deletion

A transfer past its `expiresAt` is never handed over. The object itself, though, is still sitting
in your bucket: removing it is an S3 lifecycle rule's job, and s3nd does not create one for
you. [`s3nd doctor`](/docs/cli) checks whether you have one, because a bucket quietly filling
up with expired transfers is the most common way this goes wrong.
